# RentFlow AI 产品需求文档

- 文档版本：v0.2
- 项目阶段：MVP 规划与核心能力验证
- 数据范围：以上海浦东真实区域为地理背景的合成房源
- 目标用户：租客、长租公寓运营人员、系统管理员
- 文档状态：基线版本，后续变更需要记录原因

## 1. 项目概述

RentFlow AI 是一个面向租客与长租公寓运营方的智能租赁 Agent 平台。

平台允许用户通过自然语言描述预算、户型、宠物、位置、通勤和居住偏好。系统将自然语言转换为结构化条件，使用 PostgreSQL 与 PostGIS 执行确定性筛选，使用 pgvector 处理软偏好，并由 Agent 编排搜索、解释、澄清和后续操作。

本项目当前使用合成房源，不抓取第三方平台数据，不声称房源真实可租，也不提供真实支付或合同签署能力。

## 2. 项目目标

### 2.1 产品目标

1. 用户可以使用自然语言描述租房需求。
2. 系统能够区分硬性条件、地理条件和软偏好。
3. 系统能够查询符合硬性条件和地理范围的房源。
4. 系统能够解释推荐原因，并明确说明没有满足或尚未处理的条件。
5. 高风险操作必须经过人工确认，不能由模型直接执行。
6. Agent 的输入、输出、工具调用、耗时和成本应当可追踪。

### 2.2 工程目标

1. 使用模块化单体架构完成可运行、可测试、可部署的后端系统。
2. 确定性业务规则不得由大模型替代。
3. 数据库变更必须通过 Alembic 管理。
4. 外部模型、地图和对象存储必须通过 Provider 接口隔离。
5. 核心业务应具备单元测试、集成测试和端到端测试。
6. 项目能够通过 Docker Compose 在本地复现。

### 2.3 求职展示目标

项目需要能够展示以下能力：

- FastAPI、异步编程与依赖注入；
- PostgreSQL、事务、索引与迁移；
- PostGIS 空间查询与坐标系统；
- pgvector、Embedding、混合检索与评测；
- LLM 结构化输出与防幻觉设计；
- LangGraph 状态管理、工具调用和人工审批；
- MCP 工具标准化；
- 测试、日志、追踪、限流与部署。

## 3. 非目标

MVP 阶段明确不实现：

- 抓取链家、贝壳、自如等第三方房源；
- 真实支付、押金托管或在线签约；
- 实名认证与征信；
- 真实法律意见；
- 自动退款、自动删除租客数据等高风险执行；
- Kubernetes、Kafka、服务网格；
- 为展示效果强行设计多 Agent 群聊；
- 训练或微调大模型；
- 在没有评测集的情况下宣称推荐效果优秀。

## 4. 用户角色

### 4.1 租客

租客可以：

- 使用自然语言输入租房需求；
- 使用结构化条件筛选房源；
- 查看地图、距离和房源详情；
- 对比候选房源；
- 查看推荐理由和未满足条件；
- 发起带看预约；
- 提交租后报修请求。

### 4.2 运营人员

运营人员可以：

- 创建、修改、上下架房源；
- 管理带看预约；
- 查看租客需求与 Agent 执行记录；
- 审核需要人工确认的操作；
- 管理知识库文档。

### 4.3 系统管理员

系统管理员可以：

- 管理用户和角色；
- 配置模型、地图和系统参数；
- 查看审计日志、调用成本和异常；
- 管理工具权限和风险策略。

## 5. 数据原则

### 5.1 数据定位

项目使用以上海真实区域和公共地理位置为背景的合成房源数据。

真实公共信息可以包括：

- 区域名称；
- 区域中心坐标；
- 地铁站和公共交通节点；
- 商圈、办公区、公园和医院等公共 POI。

合成信息包括：

- 具体房源；
- 租金、面积、户型、楼层与朝向；
- 宠物政策、可入住日期和描述；
- 房源状态。

### 5.2 坐标系统

系统内部统一使用 WGS84，经纬度对应 SRID 4326。

- PostGIS 使用 `Geography(Point, 4326)`；
- 距离单位统一为米；
- MapLibre/OSM 可以直接使用内部坐标；
- 接入高德 GCJ-02 或百度 BD-09 时，必须在 Provider 边界进行坐标转换。

### 5.3 数据一致性

合成数据必须满足基本业务规律：

- 户型与面积范围合理；
- 区域、面积、地铁距离与租金存在合理关系；
- 经纬度位于目标区域附近；
- 相同随机种子可以复现相同数据；
- 重复执行种子脚本不得重复插入数据。

## 6. 核心业务流程

### 6.1 结构化房源搜索

1. 用户提交区域、预算、户型、宠物、入住日期等条件。
2. API 使用 Pydantic 校验请求。
3. Service 建立事务和业务边界。
4. Repository 生成 SQL 查询。
5. PostgreSQL 返回分页结果。
6. API 返回稳定排序的房源列表和总数。

### 6.2 地理范围搜索

1. 用户提交经度、纬度和半径。
2. 三个参数必须同时存在。
3. 使用 `ST_DWithin` 执行可使用 GiST 索引的范围过滤。
4. 使用 `ST_Distance` 计算实际距离。
5. 结果按距离、租金和房源 ID 稳定排序。

### 6.3 自然语言搜索

1. 用户输入自然语言需求。
2. DeepSeek 只负责提取结构化条件。
3. Pydantic 对模型输出进行二次校验。
4. 硬性条件映射为 SQL/PostGIS 查询。
5. 尚未处理的通勤、地点或软偏好必须明确返回。
6. 系统不得因为模型输出而绕过数据库约束。

### 6.4 最终 Agent 搜索流程

目标流程为：

```text
用户需求
  → 需求解析
  → 缺失信息判断
  → 必要时向用户澄清
  → 地点解析
  → 硬条件与空间筛选
  → 软偏好语义排序
  → 推荐质量检查
  → 返回带解释的候选房源
```

## 7. 功能需求

### FR-001 服务健康检查

- 提供进程存活检查；
- 提供数据库依赖就绪检查；
- 存活检查不得因为数据库暂时不可用而失败；
- 就绪检查应反映数据库真实状态。

验收标准：

- `/api/v1/health` 返回服务名称、版本和存活状态；
- `/api/v1/health/ready` 能执行数据库轻量查询。

状态：已完成。

### FR-002 房源创建

- 支持创建合成房源；
- 必须校验租金、面积、户型、坐标和日期；
- 房源位置使用 PostGIS Geography；
- 创建失败必须回滚事务。

状态：已完成。

### FR-003 房源详情

- 根据 UUID 查询房源；
- 不存在时返回 404；
- 返回经纬度而不是 PostGIS 二进制对象。

状态：已完成。

### FR-004 确定性房源筛选

支持条件：

- 区域；
- 最高租金；
- 户型；
- 宠物政策；
- 最晚入住日期；
- 分页参数。

要求：

- 默认只展示 `available` 房源；
- 分页必须使用稳定排序；
- 单次查询数量必须设置上限；
- 返回总数、分页参数和房源列表。

状态：已完成。

### FR-005 地理半径搜索

- 经度、纬度和半径必须同时提供；
- 半径单位为米；
- 使用 `ST_DWithin` 过滤；
- 使用 `ST_Distance` 计算结果距离；
- 使用 GiST 空间索引；
- 返回距离并按距离稳定排序。

状态：已完成。

### FR-006 合成房源数据

- 默认生成 300 条上海浦东合成房源；
- 支持固定随机种子；
- 支持幂等重复运行；
- 数据生成规则需要自动化测试。

状态：已完成。

### FR-007 自然语言需求提取

输入示例：

> 预算 5000，在张江上班，通勤不超过 40 分钟，需要一室一厅，可以养猫，最好安静。

输出字段：

- 居住区域；
- 最高租金；
- 户型；
- 宠物政策；
- 最晚入住日期；
- 工作地点；
- 最大通勤时间；
- 软偏好。

要求：

- 使用 DeepSeek OpenAI-compatible API；
- 使用 JSON Output；
- 输出必须经过 Pydantic 校验；
- 不得把 API Key 写入代码或 Git；
- 空白、非法 JSON、超时和上游错误必须转换为应用异常。

状态：已完成基础能力。

### FR-008 自然语言到确定性搜索

- 将模型提取的硬条件映射为 `ListingSearchParams`；
- 调用现有 Listing Service，而不是复制 SQL；
- 未执行的条件必须返回 `unresolved_requirements`；
- 不得假装已经处理工作地点、通勤或软偏好。

状态：开发中。

### FR-009 地点解析

- 将“张江”“张江高科”等地点转换为标准地点和 WGS84 坐标；
- 第一版使用本地上海地点目录；
- 后续通过 Map Provider 接入地图服务；
- 无法识别时要求用户澄清，不得猜测坐标。

状态：未开始。

### FR-010 通勤计算

- 支持步行、骑行、公交和驾车模式的可扩展接口；
- 第一版允许使用近似计算，但必须明确标记为估算；
- 接入真实地图路线 API 后，必须保存 Provider、计算时间和结果来源；
- 通勤条件不能简单等同于直线距离。

状态：未开始。

### FR-011 软偏好语义匹配

- 为房源描述生成 Embedding；
- 使用 pgvector 保存向量；
- 支持“安静、采光好、适合独居”等软偏好；
- 先执行硬条件过滤，再进行向量召回或排序；
- Embedding 模型与向量维度必须版本化；
- 必须建立小型评测集衡量检索效果。

状态：未开始。

### FR-012 推荐解释

- 解释房源满足了哪些条件；
- 明确说明哪些条件不满足或没有处理；
- 推荐理由必须来自结构化字段或检索证据；
- 不得凭空生成周边环境、噪声或真实可租状态。

状态：未开始。

### FR-013 Agent 工作流

- 使用 LangGraph 编排需求解析、澄清、检索、排序和解释；
- 工作流状态需要可序列化；
- 节点需要具备明确输入输出；
- 外部调用需要超时、重试和错误分类；
- 工作流应支持暂停与恢复；
- 第一版使用单 Agent/显式工作流，不为展示强行拆多 Agent。

状态：未开始。

### FR-014 带看预约

- 用户可以选择房源和时间段；
- 系统检查房源状态和时间冲突；
- 创建预约需要幂等键；
- 取消和修改需要权限控制；
- Agent 可以提出预约建议，但实际创建前需要用户确认。

状态：MVP 后半阶段。

### FR-015 用户认证与权限

- 支持租客、运营人员和管理员角色；
- 使用安全密码哈希；
- API 根据角色限制房源管理、审批和系统配置；
- 用户身份、租户 ID 等安全上下文不得交给模型决定；
- 高风险工具调用必须在服务端再次鉴权。

状态：MVP 后半阶段。

### FR-016 审计与可观测性

- 记录请求 ID、用户 ID、Agent Run ID；
- 记录模型名称、Token、耗时和结果状态；
- 记录工具名称、参数摘要、耗时和错误；
- 默认不得记录 API Key、密码或完整敏感内容；
- 使用 OpenTelemetry 建立统一 Trace；
- LLM 观测平台后续接入 Langfuse。

状态：未开始。

### FR-017 MCP 工具服务

计划暴露：

- `search_listings`；
- `get_listing_detail`；
- `resolve_location`；
- `calculate_commute`；
- `create_viewing_appointment`。

要求：

- MCP handler 只负责协议转换、鉴权和错误映射；
- 业务逻辑必须复用现有 Service；
- 写操作工具必须支持人工审批与幂等。

状态：MVP 完成后。

### FR-018 多目标房源排序

- 分别计算预算、通勤、空间距离、软偏好和房源质量得分；
- 硬条件不进入可补偿评分，违反硬条件的房源不得靠高软分进入结果；
- 默认权重和用户自定义权重必须版本化；
- 返回总分、分项得分和稳定排名；
- 使用排序评测集验证结果。

状态：未开始。

### FR-019 约束冲突诊断与松弛建议

- 无结果时分析造成冲突的条件；
- 计算单个或少量条件放宽后的新增候选数量；
- 返回预算、通勤、区域或户型的最小调整建议；
- 系统不得自动接受放宽方案；
- 用户确认后创建新版本条件并重新搜索。

状态：未开始。

### FR-020 房源对比与 What-if

- 支持 2～4 套候选房源并排比较；
- 展示预算、通勤、面积、地铁、偏好和未满足条件；
- 支持调整排序权重并预览结果变化；
- 说明排名变化来源，不只返回新的总分。

状态：未开始。

### FR-021 租赁知识 RAG

- 支持租赁 FAQ、入住退租规则、演示合同和报修手册；
- 使用关键词与向量混合检索；
- 回答必须包含文档、版本、页码或章节引用；
- 无可靠证据时不得生成确定性结论；
- 合同类回答必须注明不构成法律意见。

状态：未开始。

### FR-022 文档摄取与版本管理

- 支持文档上传、哈希去重、解析、分块、Embedding 和发布；
- 摄取任务异步执行并可重试；
- 已发布版本不得被直接覆盖；
- Chunk 保留页码、章节和来源元数据。

状态：未开始。

### FR-023 RAG 引用与反馈

- 引用能够定位到具体文档版本和原文片段；
- 前端支持查看引用上下文；
- 用户可以标记回答是否有帮助；
- 引用不支持答案时应进入失败案例集。

状态：未开始。

### FR-024 Agent 与检索评测

- 维护需求提取、房源检索、排序、RAG 和工具调用数据集；
- 指标包括硬约束违规率、Recall@K、NDCG@K、引用准确率、工具成功率、成本和延迟；
- 评测记录模型、Prompt、Embedding、代码和数据版本；
- 普通 CI 使用 Stub，真实模型评测独立执行。

状态：未开始。

### FR-025 前端双端产品

- 一个 Vue 应用提供租客端和运营管理端两个 Layout；
- 租客端包含智能找房、列表地图、详情、对比、知识助手和预约；
- 运营端包含房源、预约、知识库、Agent Run、评测和看板；
- 模型提取条件、未处理条件、引用和 Agent 公开进度必须可见；
- 所有房源明确标识为合成演示数据。

状态：未开始。

## 8. 非功能需求

### NFR-001 性能

- 普通房源筛选 P95 目标小于 300 ms；
- 地理范围搜索 P95 目标小于 500 ms；
- LLM 请求单独统计，不与数据库延迟混合；
- 所有列表接口必须分页；
- 索引设计需要通过 `EXPLAIN ANALYZE` 验证。

### NFR-002 可靠性

- 外部 API 必须设置超时；
- 可重试错误和不可重试错误必须区分；
- 数据库写入需要明确事务边界；
- 写操作重试必须考虑幂等性；
- Agent 失败不得破坏已有业务数据。

### NFR-003 安全

- 密钥通过环境变量注入；
- `.env` 不得提交；
- 模型输出视为不可信输入，必须验证；
- 工具参数必须再次执行权限和业务校验；
- 防止 Prompt Injection 诱导 Agent 越权；
- 日志和 Trace 需要支持敏感字段脱敏。

### NFR-004 可测试性

- 纯规则和数据映射使用单元测试；
- Repository 与 PostGIS 查询使用集成测试；
- API 使用端到端测试；
- LLM 测试默认使用 Stub，不消耗真实 API；
- 单独维护少量真实模型评测，不混入普通 CI。

### NFR-005 可维护性

- Router 不直接编写数据库查询；
- Repository 不负责 HTTP 异常；
- Service 控制业务与事务边界；
- Provider 隔离外部厂商；
- 配置统一由 Pydantic Settings 管理；
- Python 代码使用类型标注并通过 Ruff 与 Pyright。

## 9. 系统架构

```text
Vue 3 Web
    ↓ HTTP / SSE
FastAPI Router
    ↓
Application Service / LangGraph
    ├── Listing Service
    ├── Search Service
    ├── Appointment Service
    └── Knowledge Service
    ↓
Repository / Provider
    ├── PostgreSQL + PostGIS + pgvector
    ├── DeepSeek
    ├── Map Provider
    ├── Redis / Celery
    └── MinIO
```

当前采用模块化单体。只有出现独立扩缩容、独立发布或故障隔离需求时，才考虑拆分服务。

## 12. MVP 完成定义

满足以下条件时，MVP 才算完成：

1. 用户可以用自然语言搜索上海合成房源；
2. 硬条件、空间条件和软偏好使用正确的执行方式；
3. 系统能够要求用户补充关键缺失信息；
4. 推荐结果包含来源明确的解释；
5. 至少存在一条需要用户确认的工具操作；
6. Agent 工作流可以追踪、暂停和恢复；
7. 核心流程具备自动化测试；
8. 关键查询具备索引与性能验证；
9. API Key 和敏感数据不会进入 Git 或普通日志；
10. 项目能够通过 Docker Compose 启动；
11. README 能让面试官在合理时间内理解和运行项目；
12. 存在可重复的评测集和结果报告。

## 13. 需求变更规则

后续开发遵循以下规则：

1. 每项实现必须关联一个 FR、NFR 或里程碑；
2. 新需求先更新本文档，再进入代码实现；
3. 如果需求扩大项目边界，需要说明收益、成本和延期影响；
4. 已完成需求发生行为变化时，需要更新验收标准和测试；
5. 不因出现新框架或新概念而无理由更换技术栈；
6. 优先完成当前里程碑，不同时推进多个未闭环方向。
