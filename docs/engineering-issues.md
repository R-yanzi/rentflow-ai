## ENG-001：应用工厂配置与依赖注入不一致

### 现象

健康检查测试通过 `create_app(test_settings)` 创建测试应用，但接口仍返回默认服务名称和默认版本，而不是测试配置中的值。

### 根因

应用工厂虽然接收了 `Settings`，接口却通过全局的 `get_settings` 依赖重新获取默认配置。换句话说，应用创建参数和请求处理阶段使用了两条不同的配置来源。

### 解决方案

当应用工厂收到显式配置时，通过 FastAPI 的 `dependency_overrides` 覆盖 `get_settings`，使该应用实例内的所有请求都取得同一份配置。

### 后续预防

- 配置、数据库会话和外部客户端都通过依赖注入获取；
- 测试使用应用工厂创建独立应用实例；
- 测试覆盖依赖，不修改进程级全局变量；
- 至少保留一个断言，证明测试配置确实进入了接口响应或业务逻辑。

### 面试表达

> 我们早期发现应用工厂虽然支持传入测试配置，但路由仍从全局依赖读取默认配置，导致测试隔离失效。后来使用 FastAPI 的依赖覆盖机制，让配置作用域跟随应用实例。这样测试不需要修改全局状态，也便于未来替换数据库会话和外部服务客户端。

## ENG-002：ORM 字段类型与 API 字面量类型不一致

### 现象

Pyright 报错：ORM 模型读取出的 `status` 是普通 `str`，不能传给要求 `ListingStatus` 的 Pydantic 响应模型。

### 根因

数据库约束能够保证状态值属于有限集合，但 SQLAlchemy 字段声明仍是 `Mapped[str]`。静态类型检查器无法根据数据库的 `CHECK` 约束自动推导 Python 字符串一定属于 `Literal["available", ...]`。

### 解决方案

在 ORM 到响应模型的边界使用 Pydantic `TypeAdapter(ListingStatus)` 做运行时验证。验证成功后，值在静态类型层面也被收窄为 `ListingStatus`。

### 后续预防

- 区分数据库约束、运行时校验和静态类型检查三个层次；
- 在数据跨越 ORM、领域模型、API Schema 的边界时显式转换；
- 不使用无依据的 `cast()` 掩盖可能存在的脏数据；
- 状态集合变更时同步数据库约束和 API 类型定义。

### 面试表达

> 数据库的 CHECK 约束只在数据库运行时生效，Pyright 无法据此把 `str` 推导成 Literal。我们在 ORM 到 API Schema 的边界使用 TypeAdapter 做真实校验，而不是直接 cast，因此既满足类型检查，也能防止历史脏数据绕过接口契约。

## ENG-003：重量级前端依赖导致构建包过大

### 现象

通过 `app.use(ElementPlus)` 全量注册组件后，Vite 生产构建结果为：

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 入口 JavaScript | 1,017.91 kB | 93.57 kB |
| gzip 后 | 328.76 kB | 36.37 kB |

构建同时出现单个 chunk 超过 500 kB 的警告。

### 根因

全量注册会把整个 Element Plus 组件库及其样式引入公共入口，即使当前页面只使用按钮和图标，浏览器也要下载大量未使用代码。路由懒加载无法解决公共入口已经全量引入的问题。

### 解决方案

使用 `unplugin-vue-components`、`unplugin-auto-import` 和 `ElementPlusResolver`，根据模板和代码中实际使用的组件/API自动生成导入，并保留路由级动态导入。

最终入口 JavaScript 体积减少约 90.8%，大分包警告消失。

F2 接入 MapLibre 时再次遇到了同类问题：如果在搜索结果页静态导入地图组件，约 1 MB 的地图运行时代码会进入结果页分包。这里不能依赖 tree shaking 消除 MapLibre，因为页面确实会使用完整地图能力。

因此结果页通过 `defineAsyncComponent` 动态加载地图组件，并把 MapLibre Worker 单独配置为构建资源。优化后，搜索结果页分包约为 103 kB，MapLibre 地图分包约为 1,067 kB，Worker 约为 519 kB，公共入口仍约为 109 kB。地图包本身仍然较大，但只在渲染地图时按需下载，不会污染应用公共入口；地图加载失败时，房源列表仍然可以独立使用。

### 后续预防

- 引入 UI 组件库时优先确认是否支持按需导入；
- 每次新增重量级依赖后执行生产构建并比较产物体积；
- 区分组件级按需导入与页面级路由懒加载；
- 分析构建结果时区分公共入口、页面分包和异步功能分包，不能只看最大的文件；
- 对地图、图表、富文本编辑器等确实无法裁剪的依赖，使用功能级异步加载并保留降级路径；
- 不通过调高 `chunkSizeWarningLimit` 掩盖真实体积问题；
- 后续可在 CI 中加入 bundle size budget，防止体积回退。

### 面试表达

> 项目先后遇到两类大包问题。Element Plus 是“引入了大量未使用代码”，所以通过按需导入解决；MapLibre 是“功能本身就很重”，所以通过异步组件和独立 Worker 隔离。最终公共入口保持在约 109 kB，地图只在需要时加载。我没有简单调高构建警告阈值，而是根据依赖是否可裁剪选择 tree shaking 或功能级懒加载，并保留列表模式作为降级路径。

## ENG-004：生成文件与格式检查冲突

### 现象

按需导入插件生成 `auto-imports.d.ts` 和 `components.d.ts` 后，Prettier 检查失败；即使手工格式化，插件后续重新生成时仍可能恢复原格式。

### 根因

生成文件由插件维护，但项目把它们当成人工源码执行统一格式检查，导致两个工具对同一文件拥有相互冲突的控制权。

### 解决方案

保留生成的类型声明以支持 TypeScript 和 IDE，并在 `.prettierignore` 中排除这两个文件。人工维护的源码仍然执行完整格式检查。

### 后续预防

- 明确区分源码、生成源码、构建产物和运行时数据；
- 生成文件是否提交 Git，要根据可复现性和开发体验明确约定；
- 不直接修改生成文件，修改其生成器配置；
- Lint、Format 和代码生成工具的处理范围应避免重叠冲突。

### 面试表达

> 自动生成的声明文件需要提交以保证 IDE 类型体验，但不应该由开发者手工维护。我们让生成插件拥有内容控制权，并从 Prettier 检查中排除，从而避免本地与 CI 因重复生成产生不稳定差异。

## ENG-005：用户确认的条件与实际执行条件可能不一致

### 现象

前端先调用 `/search/requirements`，把 LLM 提取的结构化条件展示给用户确认；现有 `/search/listings` 接口却只接收原始自然语言，并在搜索时再次调用 LLM。由于模型输出并非天然确定，两次解析结果可能不同。

### 根因

“自然语言一键搜索”和“解析后由用户确认再搜索”是两种不同的交互流程，但后端只提供了前一种编排接口。前端若直接复用它，就会丢失已经确认的结构化状态。

### 解决方案

新增接收 `RentalRequirements` 的 `/search/listings/confirmed` 接口，由后端把已确认条件映射成确定性数据库查询。现有自然语言一键搜索接口继续保留，并与确认搜索复用 `search_confirmed_requirements`。测试注入了一个“一旦调用就失败”的 LLM Provider，证明确认搜索不会再次调用模型。

### 后续预防

- 用户确认后的结构化数据应成为后续流程的唯一事实来源；
- LLM 负责理解非结构化输入，不负责重复决定已经确认的业务状态；
- Agent 工作流中的状态转换要显式保存，重试时不能无条件重新生成；
- 对模型调用次数设置可观测指标，避免重复调用增加延迟与成本；
- 为“确认内容等于执行内容”增加集成测试。

### 面试表达

> 我们在接前端确认流程时发现，如果确认后仍把原文交给模型重解析，第二次结果可能漂移，用户看到的条件就不一定是数据库实际执行的条件。于是把已确认的 Pydantic 结构作为唯一事实来源，后端直接映射成 SQL 条件；既提高可解释性，也减少了一次模型调用。这与 Agent 中持久化状态、避免非幂等节点重复执行是同一个设计原则。

## ENG-006：行政区与板块层级混用导致错误零召回

### 现象

用户输入“想住在浦东”时，LLM 提取 `district="浦东"`；合成房源的 `district` 字段却保存“张江、川沙、唐镇”等板块名称。数据库使用严格相等筛选，因此即使浦东存在大量房源也会返回 0 套。

### 根因

数据生成阶段把板块命名为 `district`，而需求解析和用户语义中的 `district` 指行政区。两个不同地理层级共用了同一个字段，类型同为字符串使问题直到端到端联调才暴露。

### 解决方案

将房源位置拆为行政区 `district` 与板块 `area`：通过 Alembic 将 301 条合成数据的行政区回填为“浦东新区”，原张江、金桥等值迁移到 `area`，并同步 ORM、API、搜索条件、Prompt 与前端类型。代码对“浦东”等常用别名做确定性规范化。端到端复测中，相同的浦东搜索从错误的 0 套恢复为 36 套，返回房源同时包含行政区与板块。未来 M3 再迁移到标准地点实体、别名与空间关系。

### 后续预防

- 地理字段必须明确行政层级和标准名称；
- 数据生成器、数据库模型、Prompt 和 API Schema 使用同一份领域词汇；
- 搜索测试不能只断言 SQL 参数，还要准备能命中的代表性数据；
- 0 结果需要区分真实无房、名称未规范化和层级不一致；
- 不使用模糊字符串匹配掩盖领域模型错误。

### 面试表达

> 联调时我们发现“浦东”搜索为零，但数据库有 301 套房。根因不是 SQL，而是 `district` 在模型中表示行政区，在种子数据里却表示张江、川沙等板块。我们把位置拆成 district 与 area，并用迁移修复已有数据。这个问题说明端到端测试能发现单元测试覆盖不到的领域语义错位。

## ENG-007：唯一缓存键使过期结果无法刷新

### 现象

通勤缓存使用 `request_fingerprint` 唯一约束防止并发重复写入。初版流程在有效缓存未命中后使用普通 `INSERT` 保存新结果，并在唯一约束冲突后尝试回读赢家记录。缓存首次写入、有效期内命中和模拟并发冲突的测试均能通过。

但缓存过期后，旧记录仍然占用相同指纹：查询有效缓存返回空，重新计算后的 `INSERT` 却违反唯一约束，回滚后仍然读不到有效结果。结果是同一请求在 TTL 到期后永久无法刷新。

### 根因

“唯一键防止并发重复”和“过期后追加新记录”是冲突的持久化语义。测试只覆盖单次请求分支，没有沿着“首次写入—有效命中—过期刷新”的完整生命周期验证状态变化。应用层先查后写也无法消除并发竞态，捕获所有 `IntegrityError` 还可能误判外键或检查约束错误。

### 解决方案

明确每个指纹只保留一条当前结果，Repository 使用 PostgreSQL `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 原子创建或刷新记录。过期结果和并发写入使用同一套 Upsert 语义；Service 不再捕获并猜测 `IntegrityError`，只负责计算、Upsert、提交和异常回滚。Repository 测试验证生成 SQL 包含 `ON CONFLICT DO UPDATE`，Service 测试验证未命中或过期后会重新计算并提交。

### 后续预防

- 设计缓存时同时说明唯一键、TTL、过期记录处理和并发写入策略；
- 测试完整生命周期，而不只测试单次命中与未命中分支；
- 将竞争条件交给数据库唯一约束与原子 Upsert，而不是仅靠应用层先查后写；
- 不把所有 `IntegrityError` 都解释成预期并发冲突；
- 选择追加历史还是单行刷新时，保证唯一约束与写入语义一致。

### 面试表达

> 初版通勤缓存用唯一指纹防并发重复，但仍用普通 INSERT 写入。虽然命中、未命中和并发测试都通过，沿完整生命周期推演时发现旧记录过期后仍占用唯一键，导致缓存永远无法刷新。我们改用 PostgreSQL 原子 Upsert，让过期刷新和并发合并使用同一套数据库语义，并删除了可能误判其他完整性错误的异常补救逻辑。这个问题让我意识到缓存测试要覆盖时间状态变化，而不能只看单次请求。
